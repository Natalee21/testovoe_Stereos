# testovoe_Stereos

## Установка и запуск

Требуется Node.js 18 или новее и npm.

```bash
npm install
npm run dev
```

Откройте адрес, который напечатает Next.js (обычно `http://localhost:3000`). Проверка тестов и production-сборка:

```bash
npm test
npm run build
```

## Стек и зависимости

- Next.js 14 и React 18 — локальный веб-интерфейс, обработка файлов выполняется в браузере.
- TypeScript 5 — типы документов, полей и оснований.
- Tailwind CSS 3 — минимальная адаптивная вёрстка.
- Vitest 3 — тесты нормализации, разбора, извлечения и разрешения условий на TXT из `samples/documents/` и фикстуре STN-104.

Внешние API, база данных и ключи не используются.

## Как пользоваться

1. Выберите все шесть TXT-файлов из `samples/documents/` в поле загрузки.
2. Оставьте дату проверки `10.03.2026` или задайте другую.
3. Сверьте действующие условия в таблице. Ссылка «источник» показывает файл, пункт и цитату; по нажатию исходник открывается справа на нужном абзаце.
4. В блоке «Быстрые вопросы» выберите договор и поле либо задайте дату для фильтра сроков поставки.

На учебном наборе приложение отвечает на вопросы из `docs/task.md` так:

1. **Какой срок поставки действует по STN-101 на 10.03.2026?** `30.04.2026`. В таблице источник — `02_amendment_signed.txt`, п. 2: «Поставщик обязуется поставить оборудование не позднее 30.04.2026». Сумма в этой строке показана как `1 200 000 → 1 380 000 (ДС №1, 02_amendment_signed.txt)`. Проект ДС №2 выводится отдельно как «не согласовано» со сроком `10.05.2026` и суммой `1 450 000`.
2. **Какова сумма STN-102?** `840 000 ₽`. Источник — `03_contract.txt`, п. 2.1: «Общая стоимость поставки составляет 840 000 (восемьсот сорок тысяч) рублей, включая НДС. Указанная сумма — итоговая стоимость договора.» Аванс `252 000` не подменяет сумму. В несогласованных изменениях отдельно показано письмо с предложением срока `27.03.2026`.
3. **Какова сумма STN-103?** «нет данных», поле помечено «требует проверки». Источник — `04_contract.txt`, п. 2.1: «Числовое значение стоимости в тексте договора не указано.» Лимит `600 000` не используется как стоимость.
4. **Какие поставки раньше 01.04.2026 и есть ли предложения о переносе?** Только STN-102: действующий срок `20.03.2026`, источник `03_contract.txt`, п. 3.1: «Поставщик обязуется поставить комплектующие не позднее 20.03.2026.» Рядом отмечено несогласованное предложение письма `05_supplier_email.txt`: «предлагаем перенести срок поставки с 20.03.2026 на 27.03.2026».

## Структура проекта

```text
app/                    Next.js App Router и экран приложения
components/             загрузка, таблица, быстрые вопросы, просмотрщик текста
lib/types.ts            типы и формат evidence
lib/normalize.ts        нормализация текста, сумм и дат с привязкой к оригиналу
lib/parse.ts            тип документа, номер, статус, даты, абзацы
lib/fields.config.ts    декларативные поля и шаблоны извлечения
lib/extract.ts          значения и цитаты из исходного текста
lib/resolve.ts          выбор условий на дату проверки и pending-изменения
samples/documents/      шесть неизменённых учебных TXT
tests/                  Vitest и синтетическая фикстура STN-104
docs/PLAN.md            утверждённый план и эталонные ответы
```

## Добавление поля: пример неустойки

`lib/fields.config.ts` задаёт `id`, тип (`text`, `money`, `date`), подпись и шаблоны. Для простой ставки можно добавить поле типа `text` с шаблоном, который захватывает всю фразу со ставкой и потолком, например `Неустойка за просрочку поставки составляет (0,1%[^\n]+)`. Добавьте отрицательный шаблон для фразы «Ставка неустойки в тексте договора не установлена», чтобы отсутствие значения сопровождалось citation и `needsReview`.

После изменения добавьте тесты на STN-101 (`0,1%` и `10%`), STN-102 (`0,05%` и `5%`), STN-103 (нет данных), а также на ДС, которое говорит, что неустойка остаётся без изменений. Извлечение, абзац и цитата появятся через общий pipeline. Чтобы показывать поле в таблице или быстрых вопросах, добавьте его в соответствующую разметку `components/ResultsTable.tsx` или `components/QuickQuestions.tsx` и проверьте вывод.

## Известные ограничения

- Поддерживаются только TXT-файлы в UTF-8; один файл должен содержать один документ.
- Суммы распознаются только в рублях. Валюта интерфейса — рубли.
- Извлечение основано на ожидаемых русскоязычных формулировках и структуре пунктов из задания. Новые формулировки нужно покрыть тестами; если значение не извлечено, оно отображается как «нет данных» и «требует проверки».
- Нет OCR, PDF и DOCX.
- Файлы обрабатываются в памяти вкладки и не сохраняются. Нет пользователей, авторизации и разграничения прав доступа.
- Прототип не разрешает все возможные юридические конфликты автоматически; спорные совпадающие изменения требуют проверки.
- Drag-and-drop не реализован; загрузка выполняется через стандартный выбор файлов.

## Записка продакта

**Пользователь:** специалист по закупкам, которому нужно быстро сверить действующие суммы и сроки по комплекту договора и связанных документов, не перечитывая их целиком.

**Пять вопросов клиенту перед развитием:** какие форматы и варианты формулировок встречаются в реальном архиве; что считать датой проверки и кто её задаёт; как разрешать конфликты нескольких подписанных ДС; какие поля и типы изменений критичны; какие роли и правила доступа нужны для договоров и аудита действий?

**Допущения:** один TXT — один документ; связь строится по номеру договора в тексте; условия меняет только подписанное обеими сторонами ДС, действующее к выбранной дате; письма и проекты показываются отдельно; при отсутствии значения не делаем догадок и просим проверить источник.

**Метрики полезности и качества:** доля извлечённых значений, подтверждённых пользователем без исправления; доля показанных значений с корректным переходом к подтверждающей цитате. До запуска метрик нужен ручной набор размеченных договоров.

**Архитектура и решения:** браузер передаёт TXT в функции `normalize → parse → extract → resolve`, затем таблица и просмотрщик используют один результат с цитатами. Правила вместо LLM дают воспроизводимое извлечение без API и точные цитаты, но ограничивают набор формулировок. Валидация статуса документа до применения полей предотвращает влияние писем и проектов, но неизвестные статусы требуют расширения правил. Локальная обработка без хранения проста для демо, но не даёт совместной работы, аудита и разграничения доступа.

**При 100 000 документов и доступах:** потребуется серверное индексируемое хранилище, асинхронная обработка, поиск по номеру и поставщику, версии документов, аудит и контроль доступа на уровне организации/договора. Текущая схема in-memory для такого объёма не предназначена.

**Три следующих улучшения:** 1) добавить реальные форматы и проверку качества извлечения на размеченном корпусе; 2) покрыть конфликты и более широкий набор типов допсоглашений; 3) спроектировать защищённое хранение, роли и аудит по требованиям организации.

## Отчёт о вайбкодинге

Работа началась в Cursor. При переключении на Codex обнаружились незакоммиченные файлы приложения и тестов, а UI оставался заглушкой. Сначала зафиксировано найденное состояние, затем добавлены проверки цитат, файлов-источников и абзацев для эталонных кейсов, после чего реализован интерфейс.

Характерные запросы к ИИ: «сверь незакоммиченный проект с утверждённым планом»; «усиль тесты так, чтобы цитата была подстрокой указанного исходного файла и абзаца»; «сделай таблицу договоров с переходом из источника в просмотрщик текста».

При добавлении проверок evidence первый вариант тестового helper-а обращался к массиву `citations` у уже разрешённого поля, где используется одиночный `citation`. Прогон Vitest выявил ошибку helper-а; исправлена проверка в тесте. Ошибок в `lib/` на этом шаге не обнаружено. Результат проверен полным `npm test` и production-сборкой `npm run build`.
